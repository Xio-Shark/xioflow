# xioflow 北极星：让 agent 的成果跟得上变化的世界

> 本文定义目标形态与产品取舍，不是现有 API 承诺。
> 本轮依据目录、最近 80 条提交及愿景、因果、基准文档作判断；未审阅源码、未运行测试。下列 API 与指标是设计和验收目标，不代表已实现或已达标。

## 1. 第一性原理：缺少的是成果有效性的执行契约

Agent 的推理和工具调用依赖一个会变化的世界；保存对话、重试任务和隔离进程，都不能回答旧成果现在还能否使用。

**一句话：xioflow 让 agent 在世界变化后，凭可检查的依赖证据复用仍有效的成果、重算受影响部分，并安全提交变更。**

## 2. 理想形态：可嵌入的执行内核

**首发 TypeScript 库**，嵌入现有 agent 宿主：模型、工具与上下文已经由宿主管理，同进程接入最容易明确证据和资源的责任归属，也便于逐步替换现有组合入口。

首批只承诺单机、单个 Git 工作区内的文件世界：覆盖清单、版本、工具读写及验收由适配器显式声明。未覆盖文件、网络读取和不可逆外部写入不能获得自动复用或重放保证；覆盖不足必须返回 `unknown`。

CLI 随库提供可复现演示和历史解释，复用同一契约；守护进程延后，直到跨进程共享世界的需求足以承担认证、租约和远程故障语义的成本。

### 最小接入契约

以下是拟议 API；`fileAdapter` 提供文件覆盖、观测与验收契约，`agent` 接入宿主模型与工具，示例仓库已有报价输入。

```ts
import { openWorld } from '@xioflow/kernel';
import { writeFile } from 'node:fs/promises';
import { fileAdapter, agent } from './host.js';
const world = await openWorld({ root: './repo', adapter: fileAdapter });
try {
  const step = await world.runAgentStep(agent, { task: '按 pricing.json 生成 quote.md' });
  await writeFile('./repo/pricing.json', '{"unitPrice":120}\n'); // perturb：外部改价
  const refreshed = await world.refresh(step, { onUnknown: 'recompute' });
  console.log(await world.explain(refreshed));
  const result = await world.commit(refreshed, { validation: 'strict', key: refreshed.id });
  if (result.status !== 'committed') throw new Error(result.reason);
} finally { await world.close(); }
```

`runAgentStep` 在隔离分支记录观测、上下文依赖与输出；外部写入制造真实扰动。`refresh` 只准备候选，不发布；`explain` 返回变化源、依赖路径、复用与重算节点。

`commit` 重验当前证据、输出和宿主验收，并以 OCC 发布；刷新后再次变化必须冲突。证据未知时可完整重算，仍无法建立覆盖则拒绝提交；同一 key 重试返回同一发布结果。

稳定入口收敛为 `openWorld` 与上述句柄方法；探测、共享修复、checkpoint 绑定和重试由内部状态机组合。宿主仍定义工具语义与业务验收，内核统一核验契约、推进状态和记录失败；成本预测只能选路径，不能放宽提交条件。

世界句柄持有临时事务与快照，`close` 清理已确定终态的资源；提交结果未知时保留恢复证据并返回可查询身份，不把清理成功当作提交成功。

## 3. 核心抽象与不可破坏的不变式

| 抽象 | 边界 | 必须成立的不变式 |
| --- | --- | --- |
| 世界状态 | 带覆盖清单的不可变版本，只描述有界世界。 | 固定版本在关闭重开后，覆盖清单和文件指纹必须相同；基线缺失必须失败，不能改用当前目录冒充该版本。 |
| 因果图 | 记录成果的数据与控制依赖，不自动证明依赖完整。 | 固定 `heads`、历史截止点与变化集，失效集合恰为所选祖先子图内变化节点的后继闭包（含变化节点）；无关分支与截止点之后的节点不得混入。 |
| 事务 / OCC | 候选在隔离分支计算，以当前证据决定发布。 | 同基线对同一文件写入不同内容的两个候选，在未重新刷新时最多一个可提交；发布前校验失败者不写主目录，同 key 重试不重复发布。 |
| 重放 | 区分只读历史、证据再验证与重新执行。 | 从固定快照重放完整确定性前缀，逐步哈希全部一致才可报告匹配；首个分歧或工具异常必须定位到步骤并阻止恢复绑定。 |
| 验证 | 版本、依赖覆盖、输出完整性与业务验收分别成立。 | 分别注入覆盖证据缺失、输出篡改、业务验收失败，三者均不得返回 `committed`；单独通过 OCC 不能替代任何一项。 |

`explain` 和历史查询必须只读：调用前后 journal 截止序号、工作区文件和 Run 已消耗预算不变；同一截止点在重开后得到同一证据路径。修复与历史分叉也不得回退累计预算。

完整性由适配器显式声明，内核不能凭空发现未声明的隐性读取；`null`（未跟踪）与 `[]`（声明无依赖）必须区分。模型读取了整个上下文就依赖全部相关观测；非确定性模型响应作为产物保存，失效后重新推理，不能假装重复调用模型就是确定性重放。

### 内核与插件

内核保留版本与快照、只追加 journal、依赖闭包、事务/OCC、验证、解释，以及 checkpoint 关联和未决资源状态。工具语义、模型驱动、调度与投机、成本预测和外部系统适配通过宿主或插件接入；插件只能提出候选与策略，不能跳过内核发布判定。

## 4. 向成熟系统借鉴什么

| 系统 | 借鉴 | xioflow 的边界与差异 |
| --- | --- | --- |
| Temporal | 持久执行与恢复 | 补上活动所依据的世界状态是否仍有效。 |
| LangGraph | 图编排与 checkpoint | 绑定上下文、依赖证据和工作区版本。 |
| Dagger / Nix | 隔离、可寻址产物与显式输入 | 处理交互中形成的观测依赖与可提交变更。 |
| Git | 不可变历史与分支 | 合并后还要验证工具成果及决策依据。 |
| 数据库 MVCC | 快照、版本与并发控制 | 将有界世界中的工具执行纳入提交检查。 |
| Bazel | 动态依赖与增量失效 | 将增量计算延伸到 agent 上下文与发布协议。 |

**最大的两个结构性问题：**

1. **正确性契约与资源归属没有收口。** 大量组合入口把探测、修复、绑定、OCC 和回收交给宿主拼接；文件提交与多个 checkpoint 绑定并非原子操作。必须收敛到持久状态机，分别记录准备、文件发布、逐项绑定和未知结果，不能以批次成功替代发布事实。
2. **评测按能力切片组织，缺少真实 agent 任务的收益总账。** 现有刷新样本生成调用从 8 降至 2，总调用却从 16 增至 23，中位耗时约 188→296 ms（三轮本机小负载，见 `causal-refresh-benchmark.md`）；哈希任务及 `modelTokens: null` 不能证明模型任务节省。必须统一正确性、总耗时与真实 token 口径，再决定优化方向。

## 6. 通向产品闭环 v0.1 的可验证里程碑

这里的 v0.1 指最小产品闭环，不是回退现有 kernel 包版本。以下均为待验收目标，按顺序过关；预测插件和守护进程不得抢占闭环优先级。

1. **M1：契约冻结。** 交付第 2 节入口的类型草案、状态转移表及适配器覆盖声明；证据缺失、验证异常、OCC 冲突、提交未决、同 key 重试、关闭资源六类情况均有输入、预期返回、可重试性和资源归属，缺任一项不完成。模型与工具的完整依赖无法声明时，必须存在明确的 `unknown` 路径。
2. **M2：单世界正确性闭环。** 无变化、局部变化、全部失效、依赖未跟踪、工具异常、刷新后再次改文件六类场景各重复 10 次；允许提交的结果全部匹配独立 oracle，发布前拒绝的事务不写主目录，异常不冒充变化。逐项验证第 3 节不变式；关闭重开后，同一历史截止点的解释与提交身份不变。
3. **M3：通过下述报价 demo。** 交付可复现输入、扰动脚本、完整重跑对照与逐轮 JSON 报告；正确性和成本门槛同时通过才完成，不能用节点复用率代替收益。
4. **M4：可交付与可恢复。** 从干净目录安装候选库，一个原生 TypeScript 脚本和一个 LangGraph 宿主均仅用公开入口完成 demo；配套 CLI 可运行对照并按事务 ID 查询解释。共享准备后、输出复制后、文件发布后但 checkpoint 绑定前、绑定结果持久化前四个位置各终止进程并重开 10 次：结果最终可查、同 key 不重复发布、先前成功的 checkpoint 不改写；另注入输出损坏，必须拒绝复用。终态资源可回收，未决事务及仍被历史引用的基线不误删，清理失败有可查询记录。

### 杀手级 demo：改价后，只更新受影响的客户报价

- **任务：** agent 为 20 个客户读取各自订单与按 SKU 分文件的价格，调用真实模型安排读取、计算和写入工具，生成 20 份报价及一份汇总表；金额用整数分计算，文件由固定模板渲染，便于与独立计算器逐字节核对。
- **依赖边界：** 每个客户使用独立上下文，只接收该订单及其 SKU 价格；汇总表依赖全部报价。若一个模型调用读了所有客户数据，就必须声明全部依赖，不能声称只影响两份。
- **扰动：** 首次执行完成、提交前，外部进程把 `prices/SKU-A.json` 单价从 100 元改成 120 元；只有 C01、C02 各订购两件该 SKU，且无税费折扣。两份报价应从 200 元变成 240 元，总表增加 80 元，其余 18 份报价正文哈希保持不变；解释须给出价格 → 两份报价 → 汇总的路径。
- **公平对照：** 从相同首次执行产物和历史分别开始增量刷新与完整重跑；后者重做所有报价，但同样允许共享公共输入。固定模型版本、参数、工具、缓存条件、预算及提交验证，轮换策略顺序；独立 oracle 使用扰动后的输入，不调用被测刷新逻辑。
- **计量范围：** 从扰动完成后的检测开始，到文件提交、checkpoint 绑定和终态资源回收完成，计入探测、复用验证、重算、OCC 重放、快照、分发、journal、失败及重试成本；初始化和首次执行成本单列，同时报告整个任务总成本。记录真实模型输入/输出 token、缓存 token、总工具次数、读写字节、p50/p95 延迟及逐轮失败原因。
- **局部变化门槛：** 30 组成对运行全部通过 oracle，过期成果提交为 0；增量路径只重新生成两份报价并更新总表。扰动后 p50 延迟 ≤ 完整重跑的 50%，p95 ≤ 75%，模型输入与输出 token 总数 ≤ 25%；缓存命中单列，缺少真实 usage 数据则 token 门槛未通过。
- **边界对照：** 无变化、全部 SKU 改价各跑 30 对；前者重新生成报价为 0，后者 20 份全部更新且 p50 延迟 ≤ 完整重跑的 115%；两类均须 30/30 正确。另在刷新后再次改价 10 次，旧候选必须全部冲突，重新刷新后才能提交。

未达收益门槛时，优先减少重复验证和分发开销，或缩小首发适用负载；不得省略验证、隐藏失败样本或事后挑选扰动来达标。

## 7. 此后每轮自动优化的五条原则

1. 从用户可见的失败或里程碑验收缺口开始。
2. 先保护正确性，再争取复用收益。
3. 优先合并现有能力，新增抽象必须证明必要性。
4. 用公平对照衡量端到端收益。
5. 每轮留下完整、可审查、可验证的结果。
