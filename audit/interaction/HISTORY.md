# 从计算机系统发展中寻找 Agent 与 OS 的交互机制

2026-11-03。研究对象扩大到 Agent 与系统之间的职责分配：目标怎样表达，系统信息怎样进入模型，哪些操作可以交给确定性执行层，什么时候才需要模型再次判断。下面的迁移是研究假设，历史资料只支持原机制，不能直接证明 Agent 收益。

## 可迁移机制与不可照搬的部分

| 历史机制 | 原来的改变 | 对 Agent 的研究假设 | 类比边界与反例 |
| --- | --- | --- | --- |
| Unix 管道 | 让小程序组合，结果可以直接成为下一程序的输入 | 中间数据通过引用或管道传递；模型主要选择组合和处理异常 | 动态判断仍需反馈，不能把不确定任务强行编译成静态流水线 |
| SQL 与查询优化 | 声明需要什么数据，系统选择访问路径 | Agent 表达查找、计数、存在性或更新意图；运行时选择扫描、过滤、聚合、索引 | 自然语言意图不等于正确查询；受限 DSL 也可能比现成 shell 更难用 |
| 工作集与虚拟内存 | 按使用局部性管理有限内存 | 模型上下文保存当前必要的证据，原文留在可寻址存储；按需调入、必要时预取 | LLM 注意力和有损摘要不是无损内存页；不能把简单分页改名为虚拟内存创新 |
| GUI 直接操作 | 可见对象、即时反馈、可逆的小步操作降低命令记忆负担 | 向 Agent 返回对象身份、状态、可用动作和可核查后果，减少猜路径和拼命令 | 对象可见不等于获权；屏幕式呈现未必适合模型，需比较结构化动作与代码接口 |
| 增量计算与维护查询结果 | 输入变化后复用既有计算、更新结果 | 系统维护 Agent 关心的视图，只在结果变化时请求新决策 | 文件事件不是可靠变更日志；遗漏或合并事件必须重同步，不能保证每个瞬间都被看见 |
| 端到端原则 | 放置功能时区分底层支持与应用最终正确性 | OS/runtime 提供执行事实，任务层核查用户目标是否完成 | 进程成功、退出码、动作回执都不能单独证明任务完成 |

## 原始资料

- Ritchie，1979 年报告、后续重印：[The Evolution of the Unix Time-sharing System](https://www.nokia.com/bell-labs/about/dennis-m-ritchie/hist.html)。管道部分讨论程序组合及其演化。
- Selinger 等，1979：[Access path selection in a relational database management system](https://research.ibm.com/publications/access-path-selection-in-a-relational-database-management-system)。非过程式查询与系统选择访问路径。
- Denning，1968：[The Working Set Model for Program Behavior](https://denninginstitute.com/pjd/PUBS/WSModel_1968.pdf)。根据近期使用的页面组织资源分配。
- Shneiderman，1983：[Direct Manipulation: A Step Beyond Programming Languages](https://www.cs.umd.edu/~ben/papers/Shneiderman1983Direct.pdf)。对象可见、快速反馈、渐进及可逆操作。
- McSherry 等，2013：[Differential dataflow](https://www.microsoft.com/en-us/research/publication/differential-dataflow/)。持续变化数据上的增量、迭代计算。
- Saltzer、Reed、Clark，1984：[End-to-end arguments in system design](https://web.mit.edu/saltzer/www/publications/endtoend/endtoend.pdf)。功能放置与应用端正确性的边界。

## 当前选择

按“读什么、何时读、怎样操作”推进三个问题：

1. **查询意图与执行计划**：需要一个答案时，能否把过滤、聚合、关联和中间数据传递留在系统内？比较成熟 jq/code，而非仅比较全量输出。
2. **关注状态的订阅**：Agent 声明关心哪个视图，系统只报告会影响决策的变化。先测事件、轮询、系统侧去重各自贡献，再测模型是否能正确建立和修改订阅。
3. **对象上的操作与反馈**：对象引用携带版本，运行时说明当前可行操作与失败条件，动作后提供独立验证入口。先在已有临时文件动作上检验，不扩大内核权限。

工作集、预取与增量恢复保留为这些问题的支撑机制。暂不同时实现新语言、内存系统、数据库和桌面环境。

## 本轮实验

先推进问题 2，代码与预先定义的口径见 [WATCH-PROTOCOL.md](WATCH-PROTOCOL.md)。这是由历史类比导出的机制验证，不是把常见文件监听包装成新成果。若成熟的系统侧轮询已得到同样的模型侧通知收益，必须保留该结论。

本轮已完成 18 个场景运行、54 个观察器运行和 102 个阶段末状态核对，见 [WATCH-REPORT.md](WATCH-REPORT.md)。系统侧去重轮询与事件订阅均避免了不变结果的通知；高频无关变化时，事件订阅的读取次数反而更多。当前最有依据的方向是让系统维护关注结果，再按变化模式选择触发机制。由于读取周期与核对周期不同，这不是相同发现延迟下的效率比较。

## 对研究重心的影响

从这些机制得到的共同假设是：模型负责表达目标、选择证据和处理需要判断的例外，系统负责数据搬运、重复计算、等待和可机械检查的操作前提。这是待验证的职责分配，不是历史已经证明的 AgentOS 架构。

下一步优先检验**自然语言目标能否变成正确的查询与关注条件**。例如“等待目标服务就绪，但配置变化或进程退出时重新诊断”：Agent 需要找对对象、理解就绪条件、选择订阅、知道何时证据失效。原型目前由脚本提供正确投影，这一缺口比增加更多监听接口更值得研究。

之后再比较“对象返回可用动作”与普通命令接口，衡量错误对象操作、过期前提拒绝和任务完成率。对象引用、命令执行成功和用户目标完成分别取证。每个方向都保留成熟工具对照和独立检查器；只有某个任务暴露能力缺口时才扩接口。
