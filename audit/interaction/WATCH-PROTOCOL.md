# 关注状态变化的观察实验

RFC-SI-002 · layer:research · 2026-11-03。

假设：将重复观察和相关性判断放到系统侧，可以减少需要交给 Agent 的消息；OS 事件还能在某些负载下减少系统侧扫描。两者是不同贡献，必须拆开测量。

## 对照

| 组 | 触发读取 | 发给调用方的内容 |
| --- | --- | --- |
| agent-poll | 固定周期 | 每次投影结果，包括未变化的结果 |
| server-poll | 相同周期 | 仅投影结果或可用性变化 |
| watch-view | OS 目录事件加短合并窗口，另有定期完整核对 | 仅投影结果或可用性变化 |

三组用相同文件、投影、版本和状态判定。server-poll 是强对照。消息数仅作为需要处理的通知数，不等于模型调用次数或实际模型费用。

## 工作负载与正确性

使用实验独占的临时 JSON 文件与真实 fs.watch。覆盖空闲、无关字段变化、关注字段变化、突发替换文件和人为丢弃文件事件提示。每阶段由独立解析器核对最终视图。

任务语义是维持**最近一次观察到的当前状态**，不保证记录每个短暂中间状态。OS 提示只用于触发重读，不作为状态事实。只读查询不授予写权限；任何后续操作仍须重新检查源版本。

文件替换时监视父目录，避免一直观察旧 inode；没有 filename 时保守重读。初始观测前安装监听。不可读取或 JSON 无效时明确发布 unavailable，恢复后即使视图和旧值相同也要发布恢复状态。监听错误记录为错误，不能静默变成成功。

来源：[Node fs.watch 的平台、inode 与 filename 限制](https://nodejs.org/api/fs.html#fswatchfilename-options-listener)。这里的材料化视图每次重新计算，不实现 Differential Dataflow 的增量算法。

## 指标与解释

记录真实文件读取次数、读取字节、OS 提示数、被丢弃提示数、定期核对次数、调用方消息数和消息字节；记录环境、计时参数和源码身份。

- 固定运行窗口内计数依赖调度，不应变成跨平台保证。
- watch-view 可能比低频轮询读取更多；无关事件仍有读取和过滤成本。
- 本轮轮询与定期核对间隔不同，未匹配发现延迟或状态新鲜度要求。读取次数只能描述这些配置，不证明相同延迟下的效率；下一轮须联合测量发现延迟、遗漏与开销。
- server-poll 与 watch-view 可能产生相同的消息数，这说明去重位置而非事件机制决定通知收益。
- 仅本地文件与预先声明的投影，不推断真实模型能建立正确订阅。
- 漏提示测试是显式故障注入；定期核对负责最终收敛，不冒充操作系统保证不丢事件。

## 生命周期与停止条件

所有 watcher、timer 必须在 finally 中关闭；测试验证关闭后不再读取或通知。只改新建临时文件，不启动跨会话后台服务。出现无提示错误、不可用仍标新鲜、阶段末状态不一致或资源未关闭，实验失败并修复。
